## 1. What was proven

### 1.1 The identity graph is severed — VERIFIED

There are two user tables and nothing bridges them.

| Check | Result |
|---|---|
| `public.users.id` ∩ `auth.users.id` | **0** |
| `public.users.email` ∩ `auth.users.email` | **0** |
| Trigger on `auth.users` (`handle_new_user` or similar) | **NONE** |
| `athletes.user_id` values that are an `auth.users.id` | **0** |
| `user_profiles` / `workspace_roles` rows | **0 / 0** |

`auth.users` (4 rows) is what the deployed application authorises on —
`requireWorkspaceRole()` → `auth.getUser()` → `workspace_roles`.
`public.users` (8 rows) is legacy seed data, and it is what
`jwt_tenant_ids()`, `jwt_athlete_ids()` branch 2, and `/api/v1/mcp` all resolve
through.

**Consequence:** `jwt_athlete_ids()` and `jwt_tenant_ids()` return **∅ for every
possible authenticated caller**, so every policy consuming them denies every
row. The database is safe **by disconnection, not by policy** — and no parent
portal, athlete self-service or coach scoping can function until the bridge is
built.

### 1.2 D-01a is LATENT, not live — PROVEN in a rolled-back transaction

| Test | Setup | Result |
|---|---|---|
| A | attacker signed in, no `public.users` row | 0 athletes, 0 guardians, `jwt_athlete_ids()` = 0 |
| B | attacker claims a synthetic victim | **BLOCKED — SQLSTATE 23503**, `athletes_user_id_fkey` |
| C | attacker given a `public.users` row first | **INSERT SUCCEEDED**; read victim name, DOB, guardian name and contact |

**The containment is the foreign key, not the RLS policy.** The policy checks
`user_id` and leaves `passport_athlete_id` — the identity bridge itself —
unconstrained and non-unique.

**The exploit arms the moment `auth.users` → `public.users` is bridged**, which
is exactly what onboarding requires and what the standard Supabase
`handle_new_user()` trigger does. **The repair and the vulnerability are the
same edit.** That is the single most important sentence in this phase.

**No emergency containment is warranted today** (test B), but items 1–2 of the
minimum set must land **before** anything bridges the two planes.

### 1.3 R4 is real, and it is created by deployed source — VERIFIED

Legacy codes are 3-digit (`ATH-500`…`ATH-638`); the issuer emits 5-digit
(`ATH-00505`). As strings they do not collide — **until
`migrateLegacyCode()` (`lib/services/nrhl-etl.ts:178`) pads legacy codes to
exactly five digits**, which is what it exists to do. After migration the legacy
block is `ATH-00500`…`ATH-00638` and the next issue is `ATH-00505`.

**This corrects 0.3L §5.2 and `ATHLETE_ID_SPEC.md` §3**, both of which claim
padding dissolves the collision. Padding is what creates it.

`migrateLegacyCode` has **no production caller** — tests only. R4 is armed and
has not fired. Both target tables (`nrhl_athlete`, `bigice_athlete`) are empty
and their code columns are primary keys, so a collision fails loudly rather than
merging two children — but per R15 it fails *after* burning a code, returning an
error to a family who has already paid.

**Five incompatible `ATH-*` namespaces exist.** The only one with live
production rows — `account_reference` (`ATH-9YWQ`, `ATH-WKTR`, `ATH-ZVPD`) — is
a **payment reference, not an identity**, generated by `crypto.getRandomValues`
and printed to parents.

### 1.4 `jwt_athlete_ids()` unions two incompatible key spaces — VERIFIED

Branch 1 emits passport-plane ids (`athlete.athlete_id`); branch 2 emits
app-plane ids (`athletes.id`). Measured overlap between the two sets: **zero**.
Each consumer gets a correct answer from one branch and silent noise from the
other. In test C the helper returned **7** ids while exactly **1** produced a
readable row.

**This corrects 0.3L §6.5:** coach-scoped PII visibility is *not* live. It is a
functional gap, not an exposure.

## 3. RLS baseline and the minimum containment set

Full classification of 25 identity-relevant surfaces is in the threat model
§4. `anon` holds **no table grants anywhere**. `authenticated` holds full DML on
44 tables, so deny-by-default rests entirely on policies.

**Minimum containment set for 0.4 — six items, none applied:**

| # | Change | Gate |
|---|---|---|
| 1 | Revoke write grants on `public.athletes`; `FOR ALL` policy → `SELECT` | ready |
| 2 | Unique index on `athletes.passport_athlete_id` | ready |
| 3 | Drop `tenant_isolation_policy` from `registrations`, `performance_logs` | ready |
| 4 | Revoke write grants on the 7 athlete-scoped PII tables | ready |
| 5 | `FORCE RLS` on identity/PII/money tables | **BLOCKED — §4** |
| 6 | Pin `search_path` on `generate_legacy_claim_token` | ready, low priority |

Item 3 must land **before** item 5: `settle_payment_transaction` writes
`registrations`, and under `FORCE` it would become subject to a policy that
evaluates `NULL` in a service-role connection.

Deliberately excluded: `athlytica_core` containment (unreachable; R17 warns the
obvious script weakens security), all non-identity tables, anything touching
payments.

## 4. FORCE RLS — acceptance gate, not a result

**Docker remains unavailable. No FORCE RLS behaviour is claimed as verified,
and no test written from static analysis is offered as a substitute.**

Statically provable: only 2 of 64 `public` tables are forced; without `FORCE`
the `postgres` owner bypasses every policy; every `SECURITY DEFINER` function
here is postgres-owned and therefore currently bypasses RLS entirely.

Requiring an isolated Postgres: whether `jwt_athlete_ids()` still resolves
under `FORCE`; whether policy→definer→forced-table recursion can be triggered;
whether `settle_payment_transaction` survives `FORCE` on `registrations`;
whether `service_role` is `BYPASSRLS` on this project.

The gate is written in full in the threat model §6. It is blocked on
infrastructure, not engineering.

## 5. M1 — designed, not applied

Design in [`M1_DESIGN.md`](M1_DESIGN.md). Two `SECURITY DEFINER` functions
collapsing mint-and-insert into one transaction.

**The honest distinction the brief asked for:** `scalable_id_sequence` is a
**table row, not a Postgres `SEQUENCE`**. Its increment is an ordinary `UPDATE`
and therefore *is* transactional. So both halves of the acceptance criterion are
achievable — transactional row creation **and** transactional sequence
consumption. For a native sequence the second would be impossible.

The cost is a row lock on `scalable_id_sequence` id=1 held for the duration of
every athlete creation, serialising creation across both ventures. Free at
current volume (zero athletes ever created in production), recorded as a chosen
trade. **If R4 selects Option B the trade disappears** — a non-sequential
identifier needs no shared counter.

**M1 is blocked on R4**, because the issuer's output format is M1's contract,
and blocked on Docker for the concurrency cases.

## 8. THE DECISION BOUNDARY

Three decisions. Each changes what gets built; none can be defaulted.

### D-33 — R4 identifier scheme *(see `IDENTITY_R4_ANALYSIS.md` §7)*

| Option | Consequence |
|---|---|
| **A** continue from 639 | One `UPDATE`. Bets the identity layer on 638 being the true maximum — a number D-04 has not confirmed. |
| **B** `ATH-YYYY-XXXXXX`, non-sequential, retire the sequence — **RECOMMENDED** | Both target tables are empty, so it costs two function edits today and a full FK migration later. Structurally uncollidable: the legacy regex cannot match it. Also removes M1's lock. |
| **C** `ATH-NNNNNN` six-digit from 1 | Workable, but its safety depends on also fixing `migrateLegacyCode` in another language in another file, and it leaks registration order unless assignment is randomised. |
| **D** defer | Athlete onboarding stays blocked; the first real settlement mints from the current scheme regardless. |

**Secondary:** rename `account_reference` `ATH-` → `PAY-`? *(recommended: yes —
one line, removes a permanent confusion between a payment reference and a child)*

### D-34 — D-01a containment timing

| Option | Consequence |
|---|---|
| **Now, as ordinary 0.4 work** — **RECOMMENDED** | Items 1–2 revoke a write grant no application flow uses (verified: zero writers). Near-zero risk, and it must precede any `auth.users` → `public.users` bridge. |
| Emergency migration | Not warranted — test B proves the path is blocked today. Would add urgency without adding safety. |
| After identity resolution | Every real athlete row written in the interim sits behind a policy that will be exploitable the moment the bridge lands. |

### D-35 — isolated Postgres environment

`FORCE RLS` (item 5) and M1 cases 6/9 are both blocked on it, and both are
prerequisites for Phase 0.4 completion. **Docker install, or a paid Supabase
branch, or 0.4 cannot finish.** This is an infrastructure decision, and it has
been open since Phase 0.3 §4 was stopped for the same reason.

## 9. Recommended next action, once decided

1. **D-33 = B.** Write the R4 migration: new issuer, retire the three legacy
