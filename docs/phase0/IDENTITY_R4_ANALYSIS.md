# R4 — Legacy Identity Collision: Analysis and Decision

**Phase:** 0.4 · **Date:** 2026-08-13
**Status:** analysis complete · **OWNER DECISION REQUIRED** · nothing changed.

The sequence was not touched. No identifier was minted. Every fact below was
read from the live database or from deployed source.

---

## 1. What R4 actually is

The register records R4 as *"ID sequence at 504 collides with legacy
`ATH-500`–`ATH-638`"*. That is true, but it has been recorded imprecisely twice
— including by me in 0.3L — and the imprecision changes what the fix must be.

**The collision is not automatic. It is created by a specific function in
deployed source.**

Formats emitted by the three live issuers, at `current_value = 504`:

| Issuer | Format | Next value |
|---|---|---|
| `public.nrhl_next_athlete_code()` | `'ATH-' \|\| lpad(seq,5,'0')` | **`ATH-00505`** |
| `athlytica_core.generate_scalable_athlete_code()` (trigger) | `'ATH-' \|\| lpad(seq,5,'0')` | **`ATH-00505`** |
| `public.bigice_next_athlete_code()` | `'BIIF-' \|\| YYYY \|\| '-' \|\| lpad(seq,4,'0')` | **`BIIF-2026-0505`** |

Legacy identifiers are **three-digit and unpadded**: `ATH-500` … `ATH-638`.

As strings, `ATH-00505` and `ATH-505` do not collide. **0.3L §5.2 and
`ATHLETE_ID_SPEC.md` §3 both claim the collision is dissolved by padding. That
is wrong**, and this is the correction:

```ts
// lib/services/nrhl-etl.ts:177
/** ATH-047 -> ATH-00047. Legacy ids are 3-digit, the target is 5. */
export function migrateLegacyCode(legacy: string): string | null {
  const m = /^ATH-(\d{1,5})$/i.exec(legacy.trim());
  return m ? `ATH-${m[1]!.padStart(5, "0")}` : null;
}
```

`migrateLegacyCode()` is the designated legacy-migration normaliser, and it
pads legacy codes to **exactly the width the issuer uses**. After migration the
legacy block occupies `ATH-00500` … `ATH-00638`. The issuer's next value is
`ATH-00505`.

**The collision is exact, and padding to five digits is what creates it.**
Padding to six would only help if the migration also padded to six — and this
function does not.

**VERIFIED:** `migrateLegacyCode` has **no production caller**. Its only
references are `tests/nrhl-etl.test.mts:137-139`. R4 is armed and has not
fired.

## 3. The five `ATH-*` namespaces

This is the finding that reframes R4. `ATH-` is an overloaded prefix across
five incompatible schemes, one of which is live in production and is **not an
athlete identifier at all**.

| # | Producer | Format | Example | Live rows |
|---|---|---|---|---|
| 1 | Legacy corpus (CSV) | `ATH-NNN` | `ATH-500` … `ATH-638` | 209 codes, unmigrated |
| 2 | `nrhl_next_athlete_code()`, core trigger | `ATH-NNNNN` | `ATH-00505` | 0 |
| 3 | `bigice_next_athlete_code()` | `BIIF-YYYY-NNNN` | `BIIF-2026-0505` | 0 |
| 4 | `scripts/normalize-legacy-ids.js` | `ATH-YYYY-NNNN` | `ATH-2026-0001` | 0 (D-05: retire) |
| 5 | **`/api/v1/biz/stk-push`** `account_reference` | `ATH-` + 4 random alnum | `ATH-9YWQ`, `ATH-WKTR`, `ATH-ZVPD` | **3 — the only live ones** |
| 6 | `ATHLETE_ID_SPEC.md` proposal | `ATH-NNNNNN` | `ATH-000001` | not built |

**Namespace 5 is the dangerous one.** It is a *payment reference*, generated by
`crypto.getRandomValues` at `stk-push/route.ts:86-90`, printed to parents, and
typed into M-Pesa. It is not sequential, not an identity, and shares a prefix
with four identity schemes. It is also the only one with production rows.

A support agent, an export, or a future matcher that sees `ATH-9YWQ` next to
`ATH-00505` has no way to know one is a payment reference and the other is a
child.

## 4. Blast radius

**Does anything downstream assume numeric continuity? VERIFIED: no.**
No code parses a sequence number out of a code to infer ordering, cohort or
seniority. The only numeric coupling is `migrateLegacyCode`'s zero-padding.

**External references that depend on existing identifiers — VERIFIED:**

| Surface | Depends on | Status |
|---|---|---|
| `nrhl_metric.athlete_code`, `nrhl_stat_line.athlete_code` | FK → `nrhl_athlete.athlete_code` | 0 rows |
| `bigice_athlete.nrhl_athlete_code` | FK → `nrhl_athlete.athlete_code` | 0 rows |
| `bigice_enrollment.biif_code`, `bigice_document.biif_code` | FK → `bigice_athlete.biif_code` | 0 rows |
| Certificates (`NRHL-COMP-v1`) | athlete codes | **none issued** — `nrhl_athlete` empty, freeze recommended (R8) |
| URLs / exports | — | none found |
| Parent-facing documents | `account_reference` only | 3 live, payment references |

**Nothing outside the database depends on a sequential code, because none has
ever been issued.** This is the cheapest possible moment to change the scheme.

**If the collision fires**, the failure mode is a **primary-key violation** on
`nrhl_athlete.athlete_code` — loud, not silent. Two children never silently
share an identity. But per R15 the code is minted before the insert, so the
failure burns an identifier and returns an onboarding error **to a family who
has already paid**.

## 5. Options

### Option A — Reset the sequence above the legacy block (start at 639)
Set `current_value = 638`; next issue is `ATH-00639`.

- **Effort:** one `UPDATE`. **Blast radius:** nil today.
- **Risk:** relies on 638 being the true maximum of a corpus that D-04 has not
  yet made authoritative. **The one number this option depends on is the one
  number nobody can currently vouch for.** A 639th legacy record surfacing
  after migration re-opens R4 with rows in the table.
- **Verdict:** cheap, and bets the identity layer on an unverified maximum.

### Option B — Separate the public identifier from the sequence (RECOMMENDED)
Legacy codes never become primary identifiers. They live in the identifier
ledger as scheme-qualified **claims**. New identity uses a new namespace with a
**structurally distinct** format that no padding can collapse into the legacy
one:

```
ATH-2026-7K3QP9      prefix · issue-year · 6 random base32 chars
```

- Not sequential → leaks no ordering, no cohort size, no seniority.
- Not numeric → `migrateLegacyCode`-style normalisation cannot produce it and
  cannot consume it. The regex `^ATH-(\d{1,5})$` rejects it outright.
- Collision probability across 32⁶ ≈ 10⁹ with a UNIQUE constraint: negligible,
  and a violation is a retry, not a corruption.
- `athlete_uid` (uuid) remains the only join key. This is display only.
- **Blast radius:** `nrhl_athlete.athlete_code` and `bigice_athlete.biif_code`
  are primary keys, but both tables are **empty**, so the change costs nothing
  today and cannot be done this cheaply again.
- **Retires** `scalable_id_sequence` and all three issuers rather than
  continuing them. The sequence stays at 504 as evidence and is revoked.

### Option C — Adopt `ATHLETE_ID_SPEC.md` as written (6-digit padded, start 1)
`ATH-000001`.

- **Risk:** the spec's own claim that six digits dissolves the collision is
  false while `migrateLegacyCode` pads to five. Adopting C **requires** fixing
  `migrateLegacyCode` in the same change, or the migration writes `ATH-00500`
  into a table whose issuer writes `ATH-000001` — two widths, one column.
- Sequential, so it leaks registration order unless assignment is randomised
  (the spec requires randomised assignment; that requirement is load-bearing
  and easy to lose).
- **Verdict:** workable, strictly more fragile than B, and its safety depends
  on a second edit in a different language in a different file.

### Option D — Do nothing, keep not issuing
- Zero cost, and it is the current containment.
- **Blocks M1, blocks Phase 0.5, and blocks onboarding any new athlete.** The
  Big Ice and NRHL creation paths call these issuers on settlement. The first
  real payment that reaches onboarding will mint `BIIF-2026-0505` whether or
  not R4 has been decided.

## 6. Recommendation

**Option B.** Three reasons, in order of weight:

1. **Both target tables are empty.** `nrhl_athlete` and `bigice_athlete` have
   zero rows and their code columns are primary keys. Changing an identifier
   scheme after rows exist means a data migration across every FK; changing it
   now means editing two functions. This will never be cheaper.
2. **It removes the failure mode rather than stepping around it.** A and C
   both leave a numeric identifier that a future normaliser can collapse into
   the legacy block. B makes that structurally impossible — the legacy regex
   cannot match the new format.
3. **It is the only option that does not depend on 638 being correct**, which
   matters because D-04 is open and the corpus maximum is exactly the sort of
   fact that moves when the authoritative export finally arrives.

**Also recommended regardless of the option chosen:** stop using the `ATH-`
prefix for `account_reference`. It is a payment reference, it is customer-
facing, and it is the only live `ATH-*` in the system. `PAY-9YWQ` costs one
line in `stk-push/route.ts` and removes a permanent source of confusion. The
three existing rows can keep their references — they are historical and
already printed.

## 7. THE DECISION REQUIRED

> **Which identifier scheme does Athlytica issue from Phase 0.4 onward?**
>
> - **A** — continue the sequence from 639
> - **B** — `ATH-YYYY-XXXXXX`, non-sequential, sequence retired *(recommended)*
> - **C** — `ATH-NNNNNN` six-digit padded from 1, **and** fix `migrateLegacyCode`
> - **D** — defer, and accept that athlete onboarding stays blocked
>
> **Secondary:** rename `account_reference` from `ATH-` to `PAY-`? *(recommended: yes)*

**Consequences of deferring:** M1 cannot be finalised, because M1 makes
identifier issuance atomic and the issuer's output format is its contract. An
atomic issuer pointed at the wrong scheme issues wrong identifiers reliably
instead of occasionally. **R4 is upstream of M1, and M1 is upstream of every
athlete this business onboards.**

## 8. What was NOT done

- The sequence was **not** changed. Still 504.
- No identifier was minted.
- No issuer function was altered.
- `migrateLegacyCode` was **not** edited — fixing it is part of whichever
  option is chosen, not a free-standing change.
